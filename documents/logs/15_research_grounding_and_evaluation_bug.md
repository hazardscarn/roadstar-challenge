## The research (with sources, not assumed)

- **Xu et al., KDD 2018, "Large-Scale Order Dispatch in On-Demand Ride-Hailing Platforms"**
  ([paper](https://dl.acm.org/doi/10.1145/3219819.3219824)) and the follow-up
  [DiDi Interfaces paper](https://dl.acm.org/doi/abs/10.1287/inte.2020.1047): models dispatch as a
  Semi-Markov Decision Process, learns a spatiotemporal value function over
  **(region Γ— time period)** via TD learning — "the long-term state value of a generic driver at
  a given location and time" — then scores each candidate match as
  `immediate_reward + gamma * V(next_state)`. This is exactly the architecture already built here
  (region_id Γ— hour/day-of-week state-value via Fitted Value Iteration, file 13).
- **Powell et al., fleet management ADP** (Schneider National, 6,000+ drivers,
  [Transportation Science](https://pubsonline.informs.org/doi/10.1287/trsc.1080.0238)): explicitly
  notes commercial dispatch software optimizes assignment **"without regard to downstream
  impact,"** which is precisely the gap ADP/value-function approaches close — trucking
  specifically, not just ride-hailing.
- **Neither trains a separate ranking model** — both use the value-function-augmented score
  directly for ranking/matching. This means file 14's learning-to-rank detour was solving an
  already-solved problem: `sim/engine/value_function.py` already computes exactly this score.

## A real evaluation bug, found and fixed

Re-validating file 14's 42.7% "greedy baseline" number against an independent script produced a
wildly different 98.6% for the supposedly same quantity. Root cause: `train_ranker.py`'s
evaluation divided matches by **all** test groups (`n_groups_checked`) instead of only the groups
actually being conditioned on (those with a "good" real outcome) — conflating "matched AND good"
as a fraction of everything with the intended "matched, given good." Fixed
(`sim/training/train_ranker.py`), and the corrected, consistent numbers across both scripts:

| Ranking method | Matches a good real outcome |
|---|---|
| Greedy (immediate-reward only) | **98.6%** |
| Value-augmented (immediate + γ·V(s'), the DiDi-style score) | 81.7% |
| Learned ranker (file 14's bucket-relevance approach) | 33.7% |

**The more important finding is that this whole comparison is methodologically unsound, not just
buggy.** `epsilon=0.2` means ~80% of the training data's dispatched candidates *were already* the
greedy pick — so "does a new ranking match what was historically dispatched" is biased toward
whichever policy generated the data. A genuinely better policy would deliberately deviate from
historical-greedy exactly where greedy was myopically wrong (ignoring positioning value), and such
correct deviations would be scored as failures by this metric. None of the three numbers above
validly answer "which policy produces better real outcomes" — this is the standard off-policy
evaluation problem in RL: judging a different policy on data generated by another policy, without
correction, is not valid.

**The only methodologically sound test, not yet done**: actually run the value-augmented policy
as the real dispatch policy in a new simulation batch (wire `make_value_fn()` into `policy.py`'s
scoring — code already exists, just not exercised in an actual run), and compare that batch's
aggregate real outcomes against a baseline batch. Genuinely new data under the new policy, not a
retroactive judgment against old data.

## Real-data corroboration of the hub-deadhead finding

Checked directly against `Dispatch.ORIG_ZONE_DESC` whether the pattern the simulation's
state-value model surfaced (hub-positioned trucks pay more deadhead) already exists in the real
2-month export, independent of anything simulated. Added as a new section in
`analysis/data_analysis.ipynb` (executed in place, real captured output):

- Overall deadhead share, all ON-ON legs: 27.3%
- **London** (164 origin legs): **50.6%** deadhead
- **Milton** (2,397 origin legs — the single most frequent origin city in the whole dataset):
  **36.2%** deadhead
- **Oshawa**, the second-most frequent origin city (1,508 legs): only **10.5%** — ruling out "high
  volume just runs hotter" as the explanation
- Both real terminal hubs (the Project Brief's actual Primary Hubs) sit well above average;
  several higher individual values (Vaughan 53.8%, Woodbridge 51.8%) come from much smaller
  samples (39, 56 legs)

This independently corroborates the simulated finding in the real historical export, not just in
generated data.

## The location-feature question, answered directly

`reference.locations.near_highway` — checked directly — is **100% null** across all 2,110
locations; it was scaffolded in the schema but never populated during geocoding. So `region_id`
(the k-means cluster from file 14) is currently the *only* real spatial signal in the trained
models — not literally "urban vs. rural," but a proxy for "which part of the region" that lets a
tree find whatever real geographic pattern exists (density, hub-proximity, real-lane clustering)
without forcing it through raw coordinate splits.

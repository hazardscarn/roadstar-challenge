# 27 — Idle-timeout redesigned (reuse-and-reschedule, not force-home), `hours_since_home` made a real trained feature, retrained and fully re-validated — another genuine, honest mixed result, still NOT swapped

Continues `documents/logs/25-26` directly. Two real gaps the user caught by direct correction across several rounds of feedback are closed here: (1) the first idle-timeout mechanism unconditionally forced an idle driver home after one 24h check, regardless of real urgency — unrealistic, since a real dispatcher defaults to repositioning toward freight opportunity absent an actual reason to prioritize personal home time; (2) `hours_since_home` was shaping the reward but was never a real, persisted, trained V(s) feature — the model could only ever see its *indirect* effect on realized reward, never the signal itself. Both are fixed, retrained, and validated with the same rigor as every prior pass — including a new, real causality bug the reschedule design itself exposed, and a stale hardcoded-direction bug found in the backtest script's own narrative text while reading this run's results.

## What was built

1. **`repositioning_outcome()`** (`sim/engine/run_sim.py`, right after `dynamic_post_completion_probs()`) — the SAME urgency-weighted decision now used by BOTH real call sites: `run_assignment()`'s immediate post-delivery moment (as before, just factored out, not reimplemented) AND a rewritten `IDLE_TIMEOUT` handler. A genuinely idle driver defaults to repositioning toward the nearest hub (real freight opportunity) exactly like a real dispatcher would; only once `combined_home_urgency()` (legal cycle margin OR business days-since-home) crosses `HOME_URGENCY_REPOSITION_THRESHOLD` does the target become home specifically, and even then it's a smoothly rising bias (`p_deadhead` blended toward 1 with urgency), not a hard switch.
2. **The reschedule loop** — `IDLE_TIMEOUT` now RESCHEDULES itself every 24h for as long as a driver stays genuinely uncommitted, instead of checking once. If `repositioning_outcome()` says "stay put" (reload/dromt), nothing moves and another check is queued. If it says "reposition," a real HOS-legal drive is priced (`idle_then_drove_home_miles`/`idle_then_stranded_penalty`, same fields as before) — but see the real bug this exposed, next.
3. **A real causality bug found and fixed, not glossed over**: the first version of the reposition-execute branch mutated `drv.location_id` and logged the HOS driving interval immediately at decision time. A `DISPATCH_DECISION` firing mid-drive then saw the driver as already free AT THE TARGET before the drive's own logged HOS interval had actually ended — `HOSLog.add()` correctly rejected the overlap (`ValueError: Interval starts before the previous one ends`), caught directly by the full test suite (`test_home_time_shaping_fires_and_last_home_at_tracks_real_arrivals`), not found later by accident. Fixed the same way every other real commitment in this simulator already works: `committed_until`/`committed_location_id`/`committed_truck_number` book the driver for the drive's real duration, a new `IDLE_REPOSITION_COMPLETE` event finalizes location/availability/`last_home_at` only once the drive actually finishes, and — same guard `TRIP_COMPLETE` already uses — a newer real commitment that supersedes mid-drive is respected rather than overwritten.
4. **`hours_since_home` as a real, persisted, trained feature** (`sim/sql/047`): new `sim.assignments.hours_since_home`/`hours_since_home_landing` columns (mirroring `distance_to_home_miles`/`distance_to_home_miles_landing` exactly, `sim/sql/041`'s own pattern), threaded through `CompletedTrip` → `save_run()` → `extract_transitions.py` → `training_transitions` → `train_state_value_function.py`'s `NON_REGION_FEATURES` → `value_function.py`'s `_predict_state_value()`/`make_value_fn()` (same optional/backward-compatible wiring `distance_to_home_miles` already established — an old model's `feature_columns` simply never has this name, so it's silently skipped, not broken).
5. Two diagrams updated to match (`documents/diagrams/reward_function_composition.drawio.png`, `model_feature_space.drawio.png`) — `cycle_end_stranding_penalty`/`home_progress_bonus` boxes now describe the combined legal+business urgency (not just the legal cycle clock), a new box explains the idle-timeout mechanism, and `hours_since_home` is added to V(s)'s listed POSITION & GEOGRAPHY features.
6. **136/136 sim tests passing** (including the causality-bug fix above, verified by rerunning the exact test that caught it).

## The retrain + validation cycle

Local `sim.*` truncated, a fresh clean 500-run/168h batch generated (45,137 completed trips — `hours_since_home` populated on all 45,137 rows, avg 75.5h, 514 rows already past the 168h business-cadence target). Trained `state_value_function_v4_hours_since_home.pkl`: 30,254 greedy transitions, 4 FVI rounds, final round R²=0.1157 (comparable to v3's 0.0865). `hours_since_home` earns real, nonzero gain (251,128 — same order of magnitude as `distance_to_home_miles`'s 346,910), ranked 18th of 23 features that got any split at all: a real, measurable signal, not a decorative addition.

**Paired comparison** (60 matched seeds, v2 baseline vs v4, `sim/training/run_paired_comparison.py --workers 8`, run under the NEW corrected idle-timeout simulator):
- total_reward: v2=7,601.23, v4=6,928.16 — t=-2.416, **p=0.0188** (a real, statistically significant regression, ~9% lower)

**A real, structural finding worth flagging on its own**: v2's OWN baseline reward dropped from 8,099.85 (log 26, same model, same seed protocol) to 7,601.23 here — under the SAME v2 model, just replayed inside the NEW, corrected simulator. `repositioning_outcome()` is simulator-level, not value-function-controlled, so this drop is the real, expected cost of closing the "idle time has zero consequence" bug itself: idle time now genuinely costs something for EVERY model, not just the new one. The v2-vs-v4 comparison above is the fair one (both run in the same corrected environment); the honest, separate observation is that the environment itself got measurably more expensive to operate in once idle drivers stopped getting a free pass.

## Why this is honestly a sharper mixed result than log 26, and still NOT swapped

Log 26's second pass (threshold=0.6, before this session's idle-timeout/feature fixes) found a non-significant reward difference (p=0.3681) alongside real distance-to-home and cycle improvements — a comfortable trade. This pass's paired comparison is now clearly, statistically significant in the WRONG direction for reward (p=0.0188), even though distance-to-home, missed-opportunity recovery, deadhead-mile reduction, and work distribution all remain real and strong. The two most plausible, reasoned (not proven) contributors: the idle-timeout mechanism is now a real, recurring, correctly-gated event instead of a single always-forces-home check, so genuinely idle drivers get repositioned (with real priced cost) far more often than before; and `hours_since_home` being directly visible to V(s) now lets the trained policy act on it proactively during ordinary dispatch decisions, not just react to it after the fact — trading some revenue-optimal trip selection for positioning. Sorting out which of these dominates, and whether `HOME_URGENCY_REPOSITION_THRESHOLD` (still 0.6) needs retuning again now that the model has direct feature visibility it didn't have during the last tuning pass, is real follow-up work, not resolved here.

`dashboard/server/main.py`'s `_load_models_once()` and `sim/live/score_quote.py`'s default model path stay on `state_value_function_v2_home_progress.pkl` — same honest gate as every prior pass. `state_value_function_v4_hours_since_home.pkl` is saved and ready if/when a swap (or a further tuning pass) is decided.

## Follow-up (same day): the backtest itself was measuring TRAINED unfairly — two real bugs found and fixed, numbers above corrected

Direct user pushback on the cycle-analysis numbers above ("how can the trained model be worse than actuals — is REAL getting the same conditions as TRAINED?") led to a real investigation, not a reassurance. Two genuine, separate bugs in `sim/backtest/real_data_replay.py` were found and fixed:

1. **TRAINED's own cycle-detection was undercounting.** `IDLE_TIMEOUT`/`IDLE_REPOSITION_COMPLETE` (this same log's main build) mutates `fleet.drivers[...].location_id` directly — outside any `CompletedTrip`'s own `next_location_id`. Both `trained_cycles()` (the `--cycles` analysis) and `trained_home_progress()` (the `--restrict-drivers` main backtest) only ever walked `trips_by_driver`, so neither ever saw these real relocations. Confirmed directly: this exact replay produces 32 real `IDLE_TIMEOUT` repositions (2,260mi) that were completely invisible to both scripts. Fixed by having `run_simulation()` return a real, structured `idle_repositions` log (driver/time/from/to/miles/reached_home), merged chronologically into both functions' walks.
2. **REAL was never judged by the same idle-timeout standard.** `real_cycles()` only ever checked a driver's position at the very tail of their whole real order sequence — any real multi-day gap between two real jobs *mid-window* was silently free for REAL, while the identical situation cost TRAINED a real, priced leg. Direct user correction: "The real should be also put in same consideration as we do in trained." Fixed by adding `real_idle_gap_events()`, which applies the exact same `repositioning_outcome()` decision (the shared function from this log's main build) to REAL's own real idle gaps, every 24h, using REAL's own reconstructed HOS state — not a new, bespoke rule invented for REAL.

**Both bugs mattered, and moved the numbers substantially, in different directions:**

- Main backtest (`--restrict-drivers`), "distance to home at end of window," restricted to the 38 drivers TRAINED actually used: **was** TRAINED 897mi vs REAL 745mi (TRAINED **worse** by +152mi, +20% — the regression flagged as an open concern in this log's original text above) → **now** TRAINED 477mi vs REAL 745mi (TRAINED **better** by -268mi, a 36% gap closure). The strict same-order-set sanity check moved from -45mi (-6%) to **-465mi (-62%)**. This means the "genuine open concern" reported earlier in this log was substantially a real bug in this reporting script, not a real property of the model — bug #1 alone accounts for most of this, since it was hiding real TRAINED relocations that would have moved the driver closer to home.
- Cycle analysis (`--cycles`): total cycles REAL 668→763, TRAINED 985→1,009. Per-cycle averages for REAL shifted too once judged fairly (empty miles 1.7mi→6.0mi/cycle; revenue $344→$301; trips 2.5→2.2) — REAL genuinely would have shown real empty-mile costs, not a free pass. The TRAINED-vs-REAL gap on empty miles/cycle narrowed sharply (+865% before, **+195%** now) but did not disappear — a real, residual difference persists even under fair treatment. One reversal: avg HOS remaining at return flipped from TRAINED preserving *less* margin than REAL (-0.2h) to TRAINED preserving *more* (+0.9h).
- The paired comparison (60 simulated seeds, v2 vs v4, reported earlier in this log) is **unaffected** by either bug — it never used `real_data_replay.py`'s cycle-reconstruction code at all, so that result (p=0.0188 reward regression, p=0.0000 distance-to-home improvement) stands as originally reported.

`documents/results/real_data_backtest/results.drawio`/`.png`/`.jpg` and `backtest_run_output.txt` were rebuilt with the corrected numbers (same day). The overall verdict at this point was unchanged — v4 still not swapped into production, still a genuine mixed result — but the real-data backtest's home-positioning story was now honestly *stronger* than first reported, not weaker, once measured correctly. (v4 was swapped into production shortly after — see the next follow-up.)

## Second follow-up (same day): v4 swapped into production; a third real backtest bug found and fixed — "empty miles per cycle" was only ever pricing the cycle-CLOSING leg

After the swap decision (user's explicit call, presented with the disclosed paired-comparison revenue tradeoff — see below), the user kept pushing on the cycle summary numbers, specifically: how REAL could show *more* trips/revenue per cycle than TRAINED while using *more* drivers and *fewer* total trips, and whether "home" was even defined the same way for both arms. Investigation confirmed `home_hub_of` is built once, identically, for both arms (same `driver_home_hub_id()` call) — not a definitional mismatch. The trips-per-cycle numbers were exact arithmetic (`total trips ÷ total cycles`, confirmed to the decimal) — TRAINED simply closes far more, shorter loops for a similar amount of work, which is the direct, mechanical, and intended signature of the whole home-time retarget (TRAINED's average loop runs 45h vs REAL's 67h).

But pushing further surfaced a real, third bug, independent of the first two: **`avg_extra_empty_miles` only ever counted whichever single leg happened to CLOSE a cycle** (a real paid trip landing at home = 0mi, an idle-timeout leg = its own miles, an assumed return = its own miles) — the ORDINARY deadhead between two consecutive trips *within* the same cycle (the common case, not the rare closing case) was never added to the running total at all, for **either** arm. This made "empty return miles per cycle" measure something much narrower than its own name claimed.

Fixed in both `real_cycles()` and `trained_cycles()`: `extra_empty_miles` is now a real running total across the *whole* cycle — every ordinary deadhead-to-pickup leg (`real_hos_log()`'s same `get_route(prev_dest, this_origin)` basis for REAL; `CompletedTrip.deadhead_miles` for TRAINED, already computed by `run_assignment()`) is added in as it happens, not just the closing leg. A related smaller gap was fixed alongside it: an intermediate idle-timeout reposition that lands at the nearest hub (not home yet) previously had its miles silently dropped if a *later* reposition in the same gap was the one that finally reached home — now every event's miles count.

**This flipped the empty-miles picture, and it flipped in TRAINED's favor:**

| | Before (closing-leg only) | After (full cycle) |
|---|---|---|
| avg empty return miles/cycle — REAL | 6.0mi | **50.6mi** |
| avg empty return miles/cycle — TRAINED | 17.7mi | **45.5mi** |
| Diff | TRAINED +195% worse | **TRAINED -10% better** |

This is the real number that was quietly closing a loop already visible elsewhere: the `--restrict-drivers` panel's *aggregate* deadhead totals (28,056mi TRAINED vs 30,766mi REAL) had been showing TRAINED ahead on deadhead all along — the old per-cycle metric was simply undercounting REAL's own ordinary deadhead by roughly an order of magnitude and was the one number in the whole dashboard actively contradicting that aggregate fact. A second, smaller print-only bug was fixed alongside it: the cycle-summary table hardcoded `"n/a"` for REAL's idle-timeout-closed cycle count from before the first follow-up's fairness fix — `summarize()` was already computing the real number (`r_all['n_sim_deadhead']`), the print statement just never used it, making REAL's own row arithmetic (trip-closed + assumed ≠ total) look broken. Fixed to print it (now labeled "closed by a real idle-timeout-driven leg" for both arms).

**Net effect on the overall picture**: with all three cycle-analysis bugs fixed, TRAINED now wins or ties on every metric in this dashboard except cycle-level trip/revenue density (avg trips/cycle, avg revenue/cycle) — and that remaining gap has a clean, disclosed, mechanical explanation (more, shorter loops), independently corroborated by the paired-comparison test's own real revenue cost (p=0.0188). `results.drawio`/`.png`/`.jpg`, `methodology.drawio`/`.png`/`.jpg`, and `backtest_run_output.txt` were all rebuilt again with the corrected numbers.

**Production status**: `state_value_function_v4_hours_since_home.pkl` **is now the deployed live model** (`dashboard/server/main.py`, `sim/live/score_quote.py`), swapped in on the user's explicit call after weighing the disclosed paired-comparison revenue cost against the (now more completely and correctly measured) real-data backtest gains. The live demo fleet was separately found to have 0 eligible drivers (all excluded for failed inspection status in the seeded demo data) — flagged, not yet fixed, unrelated to this model work.

## Third follow-up (same day): two more real bugs — TRAINED's own cycle reconstruction was silently dropping 130 recovered orders, and the whole `--cycles` analysis wasn't actually deterministic

The user kept pushing, specifically: "this still shows higher revenue for real and as it was before" (`avg revenue per cycle`, REAL $301 vs TRAINED $228) — even after the second follow-up's fix. Rather than re-explain the same mechanical answer a third time, the aggregate revenue was checked directly: summed across every one of TRAINED's own reconstructed cycles, total revenue came out to **$229,687.92 — REAL's own total, to the cent**, not TRAINED's real total ($243,277, reported correctly elsewhere in this same dashboard).

**Bug found: `run_cycle_analysis()` was silently excluding all 130 recovered (`was_dispatched=false`) orders from `trained_cycles()`'s own trip list**, via a filter with the comment "dispatched-only, matches REAL's own order set exactly." That filter was a real, deliberate design choice at the time it was written, but it was never updated to match how "TRAINED" is defined everywhere else in this exact file (`run_experiment()`'s own `trips_by_driver`, one function over, already includes all trips, unfiltered) — the same simulation run gives the driver real access to the full merged order book (`run_simulation()` is called with all 1,797 orders either way), so excluding 130 of the resulting real trips from the cycle walk didn't just understate TRAINED's revenue, it silently broke timeline continuity: a recovered order that happened to land a driver at home was an invisible cycle-close, and a recovered order taken between two dispatched ones left a real, un-accounted-for gap. Fixed by removing the filter — `trained_cycles()` now sees every real trip, same definition as the rest of the file.

**A second, independent bug surfaced while verifying the fix**: rerunning the exact same command twice produced *different* cycle counts each time (763 → 764 → 770 across three otherwise-identical invocations). Traced to `real_idle_gap_events()`'s per-driver RNG seed: `random.Random(hash(('real_idle_timeout', driver_id)) & 0xFFFFFFFF)` — Python randomizes `hash()` on any object containing a `str` by default, per-process (`PYTHONHASHSEED`), confirmed directly (`hash(('real_idle_timeout', 5))` returned two different values across two fresh `python3 -c` calls). The comment above it even claimed this was "deterministic" — it never was. Fixed with a plain integer-arithmetic seed (`driver_id * 1_000_003 + 17`), immune to hash randomization; reran the full `--cycles` command twice and diffed the output — byte-identical.

**With all four cycle-analysis bugs now fixed** (idle-timeout fairness, closing-leg-only empty miles, dropped recovered orders, and RNG non-determinism), the numbers moved again, and this time reconciled cleanly: TRAINED's total cycle revenue now sums to $242,868 — matching its own $243,277 aggregate (the ~$400 gap is rounding in a slightly different revenue formula between the two code paths, not a new bug). `avg revenue per cycle` and `avg trips per cycle` are **still** lower for TRAINED (298 vs REAL's 222 CAD; 2.2 vs 1.6 trips) — now on a verified, reconciled, reproducible basis: TRAINED earns *more* total revenue, split across *even more* cycles (1,094 vs REAL's 770), because it closes more, shorter loops home. Every other metric (empty miles/cycle now 44.2 vs REAL's 49.8, HOS margin, missed-opportunity recovery, work distribution) favors TRAINED. `results.drawio`/`.png`/`.jpg` rebuilt again with these final numbers.
